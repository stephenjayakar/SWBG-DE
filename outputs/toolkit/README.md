# V2 rebuild and validation

Run from the task root. These source copies document the active files under work/. Dependencies: Python 3.10, Java 21, MSVC 2022/CMake; Tapsa/genieutils commit 4c22b41ccb73c68609707f14f65c7203168f55f9 and ImWG/SMX-Workshop commit 7e2b5bcf4314ebef60fe1bc164a9eeb169ab968f.

The raw compressor adapter uses uncompressed streams. Never install a raw DAT. Source/target raw files and palettes already exist under work/ on this machine.

1. Build work/dat-tool with CMake into work/dat-build (Release).
2. Run `work/dat-build/Release/portdat.exe build-next work/de.raw work/next-mod.raw`.
3. Run `work/dat-build/Release/portdat.exe de work/next-mod.raw work/next-reloaded`.
4. Run `python work/extract_sprites.py work/next-graphic-mapping.tsv work/next-slp`.
5. In work/smx-workshop, compile PortSprites.java against Export/SMX Workshop.jar. Run `java '-Djava.awt.headless=true' -cp '.;Export/SMX Workshop.jar' PortSprites ../next-slp ../next-converted ../extracted/interfac_x2/50500.bin 1`, then repeat with ../next-converted4x and scale 2. The tool rereads and checks converted frames, pixels and anchors.
6. Run `python work/install_v2.py` from the task root. This compresses and installs Trooper-MVP (data) and Assets (media/English strings) to this machine's primary DE profile. It does not enable them or edit base game files. The existing Maps package is already installed.
7. Run `work/dat-build/Release/portdat.exe audit work/next-mod.raw work/audited-native.raw`, then `python outputs/toolkit/validate.py`.
8. Follow PLAY-ME.md for the required new-match visual test.

The audit checks that modified native units retain all serialized fields except explicitly allowed graphics, names, projectile references and animation timing. It removes the known new units/graphics and restores only known modified native unit fields, then requires the entire resulting DAT to match the native raw DAT byte for byte. This detects collateral changes; it does not prove engine compatibility or visual rendering.

The old package_mod.py/build command describes v1 and must not be used to rebuild v2. package_next.py describes an older staged intermediate. Map layout conversion uses build_maps.py, with 20 source maps and native resource replacement. Arena walls and Nova gold placement blocks are preserved. All maps still require engine generation tests.

Installed runtime files are hash-checked against packages. Metadata is compared semantically because DE updates CacheStatus and JSON formatting. Original DE DAT is unchanged; schema roundtrip is byte exact. Current results: ../validation-report.json.

Current sprites expand five SWGB direction groups into eight DE groups. Standard/enhanced scales are now 1x/2x source size.

Reserved unit IDs (mandatory, October 2026 crash fix): DE reads object IDs 900-999 as unit-class groups, and a real unit there crashes the game (`AoE2DE_s.exe+0x1356be0`, `Object Tracker Error: Added object with reserved group id`). The builder, work/ intermediates and source-parity checks keep SWGB IDs; the committed table `reserved-unit-id-remap.json` (98 units: 900->1431, 901-999->1598-1695 without 1621) is applied at the DE boundary. `install_parity_dat.py` and `package_factions.py` remap the DAT before compressing, and the generators that write DE files (faction_civs, faction_maps, faction_tree_ui, faction_nursery/faction_astromech, port_classic_ai with classic_ai_de_lines, classic_ai_observer) emit the moved IDs through `reserved_unit_ids.de_unit_id`. For any other assembled pair, including the development install (DE closed), run `remap_reserved_unit_ids.py --logic <Draft dir> --data <Assets dir>`; it is idempotent. `check_reserved_unit_ids.py` must pass before packaging; `build_installer_recipe.py`, `package_installer.py` and the release workflow run it. If a new SWGB unit ever lands in 900-999, the remap refuses; extend the table with `remap_reserved_unit_ids.py --extend-table` and commit it. Requires genieutils-py 0.1.2 (byte-exact round trip checked on every run).

Civ tech trees (October 2026 fix for the empty lobby/in-game technology trees): DE resolves `tech_tree_name` in civilizations.json only against its native civs, so the factions reuse the native names of their slots (BRITONS, FRANKS; `faction_civs.FACTIONS`), as they already do for `data_name`. `faction_tree_ui.py` writes `CivTechTrees/BRITONS.json` and `FRANKS.json` with the SWGB content. The work/-based `check_faction_tree.py` remains the source-parity check of the generator.
